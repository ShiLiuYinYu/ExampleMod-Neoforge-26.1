# 程序规范

## Git 管理

### 仓库

- **单加载器**：每个仓库仅对应一种模组加载器（如 NeoForge 或 Fabric）
- **可见性**：在首个正式版（Release）发布之前，代码仓库始终保持私有状态

### 分支

- **主分支**：`master` 分支，始终保持与最新开发进度同步
- **子分支命名规则**：基于 Minecraft 版本号隔离（例如 `1.20.1` 或 `1.19.4`）
- **分支生命周期**：主分支指向团队当前开发环境的版本，已完成的保留到版本号命名的子分支
- **开发者个人分支**：命名为 `dev-<开发者姓名>-<版本号>`（例如 `dev-shiliuyinyu-1.20.1`）

### 提交

**Commit message 格式**：`[type](scope): message`

| type     | 说明                 |
| -------- | -------------------- |
| feat     | 新增玩法/功能        |
| fix      | 修复逻辑/表现 bug    |
| docs     | 仅文档变更           |
| style    | 代码样式调整（无运行影响） |
| refactor | 重构/代码清理        |
| perf     | 性能优化             |
| test     | 添加或修改测试       |
| chore    | 更新工具/辅助脚本/杂项 |
| art      | 替换/更新美术资源    |
| asset    | 更新数据表/配置      |

**示例**：

- `feat(combat): 添加新的剑类附魔"火焰冲击"`
- `fix(worldgen): 修复末地岛屿生成错位的问题 (Fixes #42)`
- `refactor(network): 重构数据包发送逻辑以减少延迟`
- `docs(readme): 更新安装教程`
- `chore(build): 升级 ForgeGradle 到 6.0`

> 单个 Commit message 可以带多个 `[type](scope): message` 格式的消息。

## 代码风格 & 命名规范

详见 `.editorconfig` 配置，这里仅做简要描述：

- **命名体系**：总体严格执行 Java 驼峰命名规范（大驼峰）
- **类名**：大驼峰（PascalCase），如：`SolarPanelBlock`
- **方法名**：小驼峰（camelCase），如：`getEnergyCapacity()`
- **常量**：全大写 + 下划线分隔，如：`MAX_ENERGY_STORAGE`
- **特殊规则**：
    - **复数限制**：仅允许用于集合/列表类变量（如 `items`、`itemTags`），普通变量或类名禁止使用复数（如用 `item` 而非 `items`）
    - **数据生成器后缀**：所有数据生成类须以 `Provider` 结尾，如 `ModBlockLootTablesProvider`

## 审核流程

1. **提交前自查（Pre-commit）**：本地编译通过，无语法与逻辑错误。推送前先拉取最新更改！
2. **合并请求流程（MR/PR）**：向 `master` 或旧版本维护分支发起合并请求时，必须关联相应的 Issue。必须填写清晰的变更描述（Commit message）。
